# v0.0.27 Production Validation Guide

## Objective
Confirm that the v0.0.27 TLS renegotiation panic fix (issue #43) actually resolves the concurrent panic in production (`foxhound-serp-scraper` enrich stage under load).

**Context**: Unit tests and race detection are necessary but insufficient for concurrency/TLS bugs. Real validation requires:
1. Concurrent load against TLS-1.2-renegotiating servers (real SERP targets)
2. Sustained multi-goroutine enrich stage operations
3. Monitoring panic/restart counts in production logs

## Deployment Steps

### 1. Update foxhound-serp-scraper Dependency
```bash
cd foxhound-serp-scraper
go get github.com/sadewadee/foxhound@v0.0.27
go mod tidy
```

### 2. Rebuild Docker Image
```bash
docker build -t foxhound-serp-scraper:v0.0.27-niche .
```

Or with version tag:
```bash
docker build -t foxhound-serp-scraper:v0.0.27-niche-fox0.0.27 .
```

### 3. Deploy to Staging (Recommended)
Run a canary deployment to staging environment first:
```bash
docker compose -f docker-compose.staging.yaml up -d --scale enrich=2
# Run for 30 minutes under moderate load
```

Monitor logs during canary:
```bash
docker compose -f docker-compose.staging.yaml logs -f enrich | grep -i "panic\|renegot\|tls"
```

### 4. Full Production Deployment
Once canary confirms no panics, deploy to production:
```bash
docker compose -f docker-compose.yaml up -d --scale enrich=4
# or auto-scale settings
```

## Validation Checklist

### Before Deployment
- [ ] Verify foxhound-serp-scraper source branch is clean (no local mods)
- [ ] Confirm v0.0.27 is available in GitHub (tag confirmed, pushed to main)
- [ ] Check foxhound-serp-scraper CI/CD passes with v0.0.27 dependency

### During Initial Canary (First 2 Hours)
- [ ] **No panic spikes**: Check logs for `sessionController.onEnterLoadSessionCheck failed` or runtime panics
- [ ] **Steady error rate**: Enrich stage should process jobs without restart cascades
- [ ] **Latency unchanged**: Average enrich time should stay within historical baseline ±10%
- [ ] **Memory stable**: No memory leak patterns (RSS growth <5% per hour over 2h)

Log search patterns:
```bash
# Panic detection
docker logs <container> | grep -E "(panic|renegotiat|TLS|sessionController)"

# Success metrics
docker logs <container> | grep "enrich completed" | wc -l

# Error rate baseline
docker logs <container> | grep -E "(403|429|503|block)" | wc -l
```

### Extended Validation (24+ Hours)
- [ ] **Crash-free uptime**: Enrich containers run for 24h without panic-induced restart
- [ ] **Request success rate**: >98% of jobs complete without TLS errors
- [ ] **No renegotiation errors in logs**: `renegotiat` keyword should not appear in error logs
- [ ] **Proxy health stable**: No secondary issues in proxy rotation or connection pooling
- [ ] **Alert thresholds quiet**: No TLS-related alerts triggered on monitoring dashboard

## Failure Scenarios & Troubleshooting

### Scenario A: Panic Still Occurs (Same Stack)
**Symptom**: `sessionController.onEnterLoadSessionCheck failed: session is set and locked` in logs

**Action**:
1. Collect full panic stack + surrounding TLS logs
2. Confirm foxhound binary was rebuilt with v0.0.27 code (check binary version: `strings <binary> | grep "v0.0.27"`)
3. Check if panic fires in `fhttp` persistConn.readLoop goroutine (library panic, cannot recover)
4. **Escalate**: File issue comment on foxhound #43 with:
   - Docker image tag and exact foxhound version in binary
   - Full panic stack
   - Load profile (concurrent jobs, target domains, proxy type)
   - Time-to-panic after deployment

### Scenario B: Different TLS Error (New Stack)
**Symptom**: Different error stack, e.g., `tls: internal error` or `x509: certificate verification failed`

**Action**:
1. This is likely unrelated to issue #43 renegotiation fix
2. Collect error logs + affected domain list
3. Check if error is proxy-related (StrictTLSVerify behavior change)
4. **Note for dev-squad**: v0.0.20 introduced `InsecureSkipVerify=true` by default to work around azuretls pin-caching bug; if new cert error appears, may need `WithStrictTLSVerify()` review

### Scenario C: No Panic, But High Error Rate (>5% TLS Errors)
**Symptom**: Fewer panics, but TLS-related job failures spiking

**Action**:
1. Check error distribution by domain (some targets may require browser escalation)
2. Verify proxy pool health (bad proxies can trigger TLS cert errors)
3. Confirm identity consistency (mismatched UA/TLS can trigger blocks)
4. Cross-check v0.0.26 error rate — if v0.0.27 is higher, regression in TLS config handling

## Success Criteria

### Hard Requirement
✅ **Zero panics** during 24h production run of enrich stage under concurrent load (≥2 workers, ≥100 jobs/min SERP traffic)

### Soft Goals
✅ Job success rate ≥98% (same or better than v0.0.26)  
✅ Latency within ±5% of v0.0.26 baseline  
✅ No memory leaks or connection pool exhaustion
