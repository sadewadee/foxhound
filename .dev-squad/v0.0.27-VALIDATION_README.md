## The Fix in 60 Seconds

**Problem**: Foxhound v0.0.24 "fixed" TLS renegotiation panic, but the fix was a no-op. Panic still crashed production enrich stage.

**Root Cause**: azuretls applies config in this order:
1. `ModifyConfig` → sets `config.Renegotiation = RenegotiateNever` ✅
2. `ApplyPreset` → reads spec's `RenegotiationInfoExtension` and overwrites config with spec's value ❌

The Firefox preset hardcodes `RenegotiateOnceAsClient`, so the effective setting was always `RenegotiateOnceAsClient`. Panic happened on first server-initiated renegotiation.

**Solution (v0.0.27)**: Wrap `session.GetClientHelloSpec` to set every `RenegotiationInfoExtension.Renegotiation` in the returned spec to `RenegotiateNever`. This value is read by `ApplyPreset`, so it survives. No fingerprint change (wire-verified).

**Validation**: Deploy to foxhound-serp-scraper enrich stage, run 24h under concurrent load, confirm panic count = 0.

## Essential Monitoring Commands

### Panic Detection (Copy & Paste)
```bash
# Watch logs in real-time (stop with Ctrl+C)
docker logs -f enrich | grep -iE "(panic|sessionController|renegotiat)"

# Batch check (no results = ✅ good)
docker logs enrich --since 2h | grep -iE "panic"

# Count panics in period
docker logs enrich --since 24h | grep -c "panic"
```

### Success Metrics
```bash
# Job success count (increase = ✅ good)
docker logs enrich --since 1h | grep "enrich completed" | wc -l

# Error rate (decrease = ✅ good)
docker logs enrich --since 1h | grep -E "(403|429|503)" | wc -l

# Memory stable (flat = ✅ good)
docker stats --no-stream | grep enrich
```
